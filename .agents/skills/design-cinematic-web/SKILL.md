# Adaptive Web Design System

Build a project-specific interface using a common decision process and selectable visual directions. Keep the invocation name `design-cinematic-web` for continuity. Cinematic presentation is one option, not a universal requirement. Reuse principles, tokens, and appropriate components, not an identical page skeleton. Communicate in the user's language.

## Ground the design

Read existing project instructions, routes, components, design tokens, dependencies, and the user's requirements before editing. Preserve the existing stack and working flows. Do not introduce a new framework or animation engine merely to match a reference.

Establish the audience, primary task, required pages, content availability, brand constraints, and devices. Infer reasonable defaults and state material assumptions briefly. Ask only when a missing answer changes the product substantially. Do not turn a request for a design plan into deployment or implementation.

Use progressive reference routing:
- Read [style-directions.md](references/style-directions.md) to choose a visual direction; use a restrained functional direction when the task calls for it.
- Read [project-adaptation.md](references/project-adaptation.md) to choose information architecture and per-page intensity.
- Read [visual-language.md](references/visual-language.md) only for the original spatial/grid direction; its neon colors and display sizes are not global defaults.
- Read [reference-observations.md](references/reference-observations.md) when grounding decisions in the three additional videos.
- Read [motion-and-delivery.md](references/motion-and-delivery.md) when implementing or testing motion.
- Read [page-system.md](references/page-system.md) for multipage interfaces, task flows, content systems, and final review.
These references are self-contained; source videos are not required at runtime.

Distinguish observed appearance from implementation hypotheses. Never claim the reference was generated by a particular AI model, uses a particular library, or implements scroll-driven interaction without evidence. Ignore promotional captions and platform watermarks when designing.

## Produce a project-specific direction

Before implementation, form a compact design contract, inline unless the project benefits from a saved specification:

- Product, audience, core task, and primary action.
- Page families and navigation; determine these from actual user journeys.
- Primary visual direction, up to one supporting influence, and three specific design decisions with their role in this project. Separate brand direction from page function.
- Semantic palette, font roles, spacing, media strategy, and content density.
- Motion intensity: expressive, balanced, or restrained; specify which regions move.
- Mobile, reduced-motion, missing-asset, and graphics-failure alternatives.
- Existing components and dependencies to reuse.

Choose the structure first, then the visual treatment. A gallery, dashboard, product catalog, and article require different information architecture. Never force all of them into hero → three feature cards → testimonials → CTA.

## Route the requested work

For analysis or design-only requests, deliver the requested critique, architecture, or design contract without building. For new websites, define the required routes and complete the requested user journeys. For redesigns, map existing features and retain working data, content, URLs, and flows unless change is requested. For small refinements, apply only relevant guidance rather than redesigning the whole site.

A shared skill can support many website categories but does not replace domain requirements, original assets, functional integrations, or testing. If the category is absent from the examples, classify its primary tasks (discover, compare, transact, read, create, manage, monitor), then derive the page families. Do not claim universal production completeness.

## Preserve the selected design identity

Build an intentional hierarchy using the selected direction: contrasting scale, aligned information, media where useful, and coherent editorial or technical framing. Depth, grids, giant type, and glow are optional; do not impose them on functional screens. Integrate a few coherent signatures rather than piling on effects. Let brand and content determine color and imagery.

Use large typography in selected storytelling areas, with practical text sizes in task areas. Keep primary actions clearly identifiable. Put fine grids and glows behind content; use opaque readable surfaces where required. Make decorative layers noninteractive and hide them from assistive technology.

Use authentic supplied or appropriately sourced media. Label temporary assets or sample data accurately. If essential 3D or video assets are missing, use a deliberate static or CSS composition and state the limitation. Do not replace an art-directed media scene with unrelated emoji or generic gradient blobs.

Never copy reference logos, client projects, text, or distinctive brand assets into another project by default. Preserve the visual principles while creating a new composition. Avoid implying that the user owns source assets or that a library can recreate them automatically.

## Implement progressively

Deliver semantic HTML, navigation, content, and core interactions first. Add reusable tokens and components suited to the actual page families. Layer the selected visual treatment over this working baseline. Define global brand tokens, page-family density/layout variants, and explicit component states rather than global CSS that makes every page look like a hero.

Use CSS transforms for simple planar depth; use an existing animation library for coordinated timelines if appropriate; use WebGL only for genuine scene requirements. A video or rendered image can be a valid solution. Read current official documentation if an unfamiliar or version-sensitive API is needed.

Keep all essential content and controls in accessible DOM. Retain native scrolling by default. Avoid making navigation depend on a drag gesture, a hover state, a custom cursor, or completion of a long intro. Do not hide body content until JavaScript or media loads.

Apply motion primarily to transform and opacity. Define a single animation owner per property, clean up listeners and rendering loops, stop offscreen or hidden scenes, and provide static alternatives. Do not add multiple competing scrolling or animation engines.

Support real UI states for requested features: focus, active, disabled, loading, empty, error, and success as applicable. Do not invent backend success, transactions, client endorsements, or operational integrations.

## Verify the result

Inspect representative desktop and mobile views using available local preview tools. Check that the result retains its selected visual character with motion disabled. Do not require cinematic signatures from a deliberately restrained direction. Verify keyboard navigation, focus visibility, text readability, touch controls, overflow, and the primary task. Check graphics/media failure and slow loading when heavy assets are used.

For application pages, verify the task before decorative polish. For an expressive landing page, verify both the storytelling sequence and an immediate path to the action. Compare screenshots against the chosen design contract, not merely the source video.

Report what was built, how it adapts to the project, what was actually verified, and any remaining limitations. Do not claim runtime, accessibility, or performance tests that were not run. Keep deployment and external actions within the user's request and the host environment's applicable workflow.
